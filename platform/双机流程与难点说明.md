# 双机森林消防系统：建议流程、平台改进与联调难点

适用设备：巡检端 Intel NUC13 / Ubuntu20.04、云卓 C12 云台、PX4；灭火端 PX4、四路舵机、无载荷反馈传感器。无线网络暂用手机热点。本文未假定具体 NUC SKU、PX4 版本、图传空端型号或舵机接线；这些仍需确认。

## 结论

建议采用“机载识别 + 独立视频分发 + 结构化火点上报 + 人工核验交接”的架构。先完成发现、看见、定位、记录，再接入经过验证的任务执行系统。**不要让 AI 检测框直接触发灭火载荷释放。**保留遥控员独立控制、原视频和飞控失联保护；平台断网不能切断操纵链路。

本次交付是可运行的双机平台联调版，不是完整机载识别/自动作业系统。没有在你的真实设备上安装模型、部署媒体服务或验证地面定位，也没有修改原公网平台。

## 一、优化后的数据流

```text
巡检机 C12 ──机内以太网── NUC13
   │                       ├─ 解码 → 推理/跟踪 → 标注视频 → 媒体服务器
   │                       │                              ├─ WebRTC/HLS → 网页平台
   │                       │                              └─ 可达RTSP输出 → 遥控器QGC
   │                       └─ 火源候选/坐标/误差/时间戳 ─HTTPS→ 平台核验列表
   └─ 原始视频 → 保留原有遥控观看链路（条件允许，作为回退）

两架 PX4 ─各自数传→ 各自QGC ─两个独立转发端口→ 平台遥测与地图
灭火机视频 ─图传或独立网络上传→ 媒体服务器 → 平台

火源候选 → 人工确认火情与地面坐标 → 任务交接给灭火机操作员
         → 操作员执行 → 人工报告 → 巡检复查/现场核验 → 留档
```

目前平台中的“交接”和“操作员报告”只是记录，未向 PX4 或舵机发命令。后续如果接入厂家执行系统，必须区分请求发送、飞控接受、执行中、实际释放、现场效果五种状态；一条ACK不能证明灭火成功。

### 减少遥控端操作

一次配置各 QGC 的固定转发目的地址、自动连接和视频源；日常只启动系统、核验火点和完成必要人工确认。避免每次导出文件。已上传飞控的普通任务，可在后续有双向、只读任务下载能力的网关上按 MAVLink Mission 协议自动读取；**QGC单向转发不足以保证主动任务下载**。尚未上传的QGC草稿只能通过文件导出/同步或改造QGC获取，不能凭空从遥测得到。

当前版本保留 `.plan` 导入展示；不会将文件直接当作 MAVLink 视频或自动执行任务。

## 二、C12 接口已经查到，但还需核对实物

依据[云卓官方 C12 手册](https://file.skydroid.xin/shuomingshu/C12-Instructions.pdf)接口与网络页：

| 项目 | 手册内容/当前判定 |
|---|---|
| 视频接口 | 以太网；需要对应厂家线束，不能盲接PoE或按通用RJ45线序供电 |
| 可见光流 | `rtsp://192.168.144.108:554/stream=1` |
| 热成像流 | `rtsp://192.168.144.108:555/stream=2` |
| 可见光实时流 | 手册标注1280×720；机内录像分辨率不等同于RTSP实时流 |
| 热成像分辨率 | 手册标注384×288、帧率≤25Hz |
| 绝对测温能力 | 不能仅凭热成像画面认定支持温度测量，需要厂家确认温度数据接口和标定 |

所以此前 `stream=0` 失败不能直接认定是 VLC 故障。先按手册路径测试，仍需验证你的C12固件是否一致。

机内优先采用有线连接：C12与NUC接厂家认可的以太网接线/交换机，NUC有线网卡设置同网段未占用静态IP；该接口通常不设置互联网默认网关。NUC另通过Wi-Fi接手机热点上网。两条链路使用不同网段，避免默认路由冲突。摄像机网络到图传空端的共享/转发方式必须看实际拓扑。

两架C12可能具有相同出厂IP：机内网络相互隔离通常没问题；接到同一个二层网络就会冲突，必须事先规划。

## 三、NUC13 图像处理建议

先测通原始流，再测转码，再接模型，最后加地面定位。NUC13具体CPU/iGPU未知，不能保证某模型720p实时帧率。

- 尽量硬件解码/编码；Intel核显可评估VA-API、Quick Sync、OpenVINO，但必须匹配实际芯片、驱动、运行库版本。
- 解码、推理、编码解耦，队列有上限；推理慢时丢弃过期推理帧，不能让延迟无限积累。
- 模型推理帧率与视频播放帧率分开调试，标注须有对应帧时间戳，不把旧框贴到新画面。
- 可见光和热成像联合确认比单纯可见光颜色阈值更合适，但两路有时差和视差，需要标定与同步。
- 保存短时环形录像、触发前后片段和识别元数据；磁盘限额与轮转必需。
- 视频流只上传一份给媒体服务器，由服务器分发给多人；不要让每个网页都直接反复拉机载流。

NUC能看到RTSP并不意味着能把处理后画面“塞回”原厂图传空端。需要确认空端是否接受NUC产生的网络流，或至少允许遥控器路由访问NUC。若不支持，只能增加可行的数据路径、经服务器回传，或选有对应接口的图传设备；不能承诺改一个URL就解决。

## 四、视频给遥控器和平台的区别

[QGC 4.4.3官方设置文档](https://docs.qgroundcontrol.com/v4.4.3/en/qgc-user-guide/settings_view/general.html)列有RTSP等视频源。QGC可测试指向处理后RTSP输出，但前提是该地址从遥控器可达，编码格式受支持。

浏览器不能直接当VLC使用RTSP。可评估[MediaMTX](https://mediamtx.org/docs/kickoff/introduction)做分发：机载到服务器采用适合网络的发布协议；浏览器采用WebRTC或HLS；遥控器采用可达RTSP。具体发布和鉴权按[官方配置文档](https://mediamtx.org/docs/references/configuration-file)实施，不能把裸UDP或无密码RTSP直接暴露公网。

公网WebRTC需处理NAT、ICE/TURN；HLS一般更易分发但延迟特征不同。用实测端到端延迟决定是否可用于观察，**平台视频不要作为唯一操纵依据**。

手机热点仅作为地面和短距联调方案：两架飞机同时上传会共享上行带宽，且受距离、遮挡、天线方向、手机温控和省电影响。举例：两路各3Mb/s约需6Mb/s持续上行，再加协议开销和余量；这只是预算示例，不是你的设备实测码率。正式使用应做覆盖测试并选独立链路，原有遥控链路仍需保留。

## 五、最关键的难点：火源在哪，而不是飞机在哪

平台收到飞机GPS后能在地图显示飞机位置，但这不是火源坐标。斜视画面中火点可能距离飞机很远。

把检测框换成地面坐标通常需要：相机内参/畸变、变焦参数、云台相对机体姿态、飞机位置与姿态、同一时刻的时间同步，以及测距或地形表面约束。林区地形起伏、树冠遮挡和烟雾都会放大误差。热成像与可见光还需处理两个光轴的偏移。

先让系统上报“候选+截图/录像索引+误差估计”，采用人工对地标核验。没有可靠定位方法时，不制造一个看起来精确的坐标；没有坐标的事件只可登记，不能进入有效任务。平台已实现这条约束，并支持核验阶段补充坐标。

地图使用WGS84火点与遥测坐标；接入其他国内地图时必须确认其坐标系和转换要求，避免显示偏移。高度必须明确是相对起飞点、海拔还是相对地形。

## 六、四路舵机与安全反馈

四个舵机“收到动作指令”不等于四个载荷“已经脱离”。卡滞、空载、断电、接线和连杆故障都可能看起来指令正常。

当前平台四个槽位初始均为“状态未知”，操作后只能“人工报告”。建议后续增加适合装置的限位、霍尔或重量反馈，并分别验证载荷在位/释放状态。保护电源和反馈链路，避免舵机电流冲击使NUC或飞控重启。

PX4包裹投放/夹爪功能有版本和接口条件。参考[PX4官方包裹投放说明](https://docs.px4.io/main/en/flying/package_delivery_mission)时，必须核对实际固件和厂家装置；四路PWM不天然等同于四个受支持的独立夹爪。本文不提供未经实机验证的自动释放参数或流程。

## 七、主要难点与验收办法

以下覆盖当前已知主要风险；硬件型号和现场测试可能暴露更多问题，不应理解为绝对穷尽。

| 优先级 | 难点 | 对策与验收 |
|---|---|---|
| P0 | C12线束/供电未知 | 向厂家索取引脚、供电及空端拓扑，先独立有线拉流；不得盲接 |
| P0 | 处理流回到遥控器 | 验证空端接入与路由；同时验证原视频回退，不以公网流替代操纵链路 |
| P0 | 火源地理定位 | 标定、时间同步、测距/地形、误差预算；用已知地面目标实测误差 |
| P0 | 四舵机无反馈 | 手动报告和传感器结果分开；设计在位/释放检测并台架验证 |
| P0 | AI误报/漏报 | 区分候选和确认；林区真实样本评估，关注烟雾、反光、云影、热地物 |
| P0 | 双机航路冲突 | 人工划分作业区/高度层与独立操作员协调；平台不做自动避碰承诺 |
| P0 | 失联/掉电 | 独立遥控与飞控失效保护，受控地面测试断开平台、热点、机载进程 |
| P1 | C12热成像是否支持测温 | 厂家确认数据格式；没有温度标定就不用摄氏度阈值作真实温度判断 |
| P1 | 小火点与树冠遮挡 | 按高度/视角分组评估检出率；规划重访，不把未检出等同无火 |
| P1 | 两路视频时间/光轴不一致 | 建立跨相机标定与时间关联，评估运动时偏差 |
| P1 | NUC性能与发热 | 测整链路CPU/GPU、内存、温度、功耗和长时丢帧；不能只测模型FPS |
| P1 | 飞机载荷与供电 | 实测重量、重心、续航余量，固定、防振、散热及供电保护 |
| P1 | 热点覆盖与上行 | 两机同时运行实测码率/丢包/延迟，覆盖范围内外分别测试恢复 |
| P1 | 浏览器播放/NAT | 检验WebRTC连接及TURN、HTTPS混合内容和浏览器解码能力 |
| P1 | 时延与队列积压 | 时间戳贯穿采集、推理、发布、显示；缓冲有界，标记过期结果 |
| P1 | 同编号/同IP混淆 | 双UDP端口角色隔离、设备身份绑定；生产从可信网关鉴权 |
| P1 | GPS无定位/跳变 | 显示未知和时间，不沿用旧值冒充实时；比较已知地面参考 |
| P1 | 坐标系与高度基准 | WGS84与地图投影/其他偏移坐标明确；航点标注高度基准 |
| P1 | QGC草稿与飞控任务不一致 | 区分导入文件、已上传任务、当前任务版本；不静默覆盖 |
| P1 | 指令重试与重复投放 | 未来执行层需身份、有效期、幂等、状态机和独立人工许可；当前不开放执行接口 |
| P1 | 多次检测同一火点 | 机载跟踪事件ID、时间/空间聚类；当前仅eventKey精确去重 |
| P1 | 数据持久化与离线 | 上报队列有时限，恢复重试不重复建任务，测试重启与磁盘写满 |
| P1 | 账号/鉴权/视频泄露 | HTTPS、用户角色、独立设备凭证、审计与最小权限；勿裸露MAVLink控制端口 |
| P2 | 地图清晰度/离线 | 选择合法影像源，测试当地最高有效级别；离线缓存按服务条款实施 |
| P2 | 记录留存与磁盘 | 环形视频、事件片段、存储配额/备份/留存期限；当前平台不是录像服务器 |
| P2 | 运维版本 | 明确Ubuntu、内核、驱动、PX4、QGC和模型版本，变更可回滚，先测试再升级 |
| P0 | 实际作业批准与现场安全 | 由有资质人员核验当地运行要求、场地人员隔离、空域和消防作业条件；软件交付不是作业许可 |

## 八、平台本次已改进与未完成

已实现：双机独立遥测、卫星地图源切换/缩放、双机实测轨迹、普通航点规划展示、两个视频播放入口、带位置误差范围的火点、候选/核验/排除、人工任务交接、四槽位报告、审计、JSON落盘、上报密钥与去重、明确演示模式、停止服务释放端口。

未完成且需要下一阶段工程：NUC真实采集与AI模型部署、双路标定和地面定位、截图/视频证据上传与存储、媒体服务器和公网鉴权、QGC自动任务同步、PX4任务执行适配、舵机传感反馈、生产数据库/多账户权限/告警归档。没有把这些包装成已完成。

## 九、建议实施顺序

1. **地面基础连通**：拆桨/解除作业载荷条件下完成C12→NUC原视频，保存网络拓扑和固件信息。
2. **无AI视频闭环**：NUC转推同一画面，遥控器与平台都能观看；测双机并发时延、断线恢复与原视频回退。
3. **只做候选识别**：接入选定模型，保存证据，平台人工核验；暂不自动生成可执行任务。
4. **验证地面定位**：已知目标和不同高度/云台角度下实测，给出误差分布而不是只看一个成功点。
5. **人工协同作业验证**：任务交接、操作员回报、巡检复核；无传感器时保持结果不确定标志。
6. **正式系统工程化**：独立通信链路、传感反馈、账户权限、设备鉴权、备份监控与长时测试。任务执行接口单独评审和验收。

## 十、下一步需要你补充

- NUC13准确型号、内存、是否独显；C12线束/网口、图传空端型号与接线照片。
- 两架PX4的固件版本、两架遥控器型号；灭火机的视频如何接出。
- 是否能够在地面同时连接C12、NUC和空端；NUC/遥控器分别能否访问对方IP。
- 四舵机装置的厂家接口文档和电源方案（暂不需要实际释放测试）。

先解决接口和视频闭环，通常比直接训练模型、直接做全自动派遣更有价值：否则平台能展示按钮，却没有可靠的数据和执行依据。
